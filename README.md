# KEPIL — город на гарантии

Муниципальная система гарантийного обслуживания инфраструктуры Актау. Инспектор регистрирует дефект → PostgreSQL проверяет гарантию → назначает подрядчика и сроки → подрядчик прикладывает подтверждение → инспектор принимает ремонт или возвращает на доработку.

**Статус поставки:** исходный проект реализован, локальная сборка и SQL-тесты проходят. Рабочий облачный Supabase пока не подключён, seed в облаке не запускался, публичного развёртывания нет. Без конфигурации приложение честно показывает `/setup`. Нельзя считать проверенными облачную авторизацию, загрузку в настоящий Storage и полный браузерный сценарий до подключения проекта.

## Запуск

Требуется Node.js 22+ и новый проект Supabase. Проверено на Node 24.

```powershell
npm ci
Copy-Item .env.example .env.local
```

1. В новом проекте Supabase выполните **по порядку, каждый файл один раз** обе миграции из `supabase/migrations/`: `20260924174728_initial_kepil.sql`, затем `20260925032029_warranty_read_model_and_evidence_limits.sql`. Либо используйте Supabase CLI: `npx supabase link --project-ref YOUR_REF`, затем `npx supabase db push`. Начальная миграция предназначена для пустой базы; не выполняйте её поверх чужой схемы. Если начальная уже применена, выполните только новую. Отдельной конкурирующей схемы нет; тесты исполняют эту же цепочку миграций.
2. В `.env.local` задайте переменные ниже. Publishable key доступен в настройках API Supabase. Service-role key нужен только скрипту начального наполнения.
3. Выполните `npm run seed`. Скрипт создаёт учётные записи, организации, 14 объектов, 13 гарантий, 9 исторических дефектов и 8 заявок. Пароли существующих аккаунтов не изменяет; повторный запуск сохраняет существующие записи и дозаполняет прерванное наполнение.
4. Выполните `npm run dev`; откройте http://localhost:3000.

| Переменная | Назначение |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | URL выбранного Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ, запросы ограничены RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | Серверный административный ключ, **только для seed** |
| `DEMO_PASSWORD` | Выбранный вами пароль новых демо-аккаунтов, минимум 12 символов |

Не передавайте service-role key в браузер или переменную с `NEXT_PUBLIC_`. Приложению в рабочем окружении достаточно первых двух переменных. `.env.local` игнорируется Git. Роли назначаются административным seed, а не через пользовательские metadata.

## Архитектура

```text
Next.js App Router / React / TypeScript / Tailwind
                  ↓ Server Actions
Supabase Auth → серверная проверка пользователя и профиля → Zod
                  ↓ RPC с JWT пользователя
PostgreSQL: транзакции, блокировки, бизнес-правила, RLS
                  ↓
Приватный Supabase Storage / история / аудит / уведомления
```

Браузер не хранит базу в localStorage. Все экраны читают Supabase через сервер. RPC используют настоящую проверенную сессию. Критические функции находятся в закрытой схеме `private`; публичные SQL-обёртки работают как `SECURITY INVOKER`. Внутренние привилегированные операции проверяют `auth.uid()`, профиль и владение заявкой. У `authenticated` нет прямых прав изменения бизнес-таблиц. RLS включён на всех 13 публичных таблицах. Представление `claims_overview` использует `security_invoker=true`.

### Модель данных

| Таблица | Содержание |
|---|---|
| organizations | Муниципальные организации и подрядчики |
| profiles | Пользователь Supabase Auth, роль, организация |
| contractors | Реквизиты и контакты ответственного подрядчика |
| contracts | Договор, исполнитель, сроки |
| assets | Объект, микрорайон, адрес, тип, договор |
| warranties | Гарантия объекта, подрядчик, начало и окончание |
| defects | Дефект, категория, критичность, повторяемость, idempotency key |
| warranty_claims | Заявка, состояние, сроки, даты исполнения и приёмки |
| claim_evidence | Подтверждения и пути приватных файлов |
| inspections | Решения инспектора и комментарии |
| status_history | История переходов объекта процесса, автор, причина |
| notifications | Внутренние уведомления пользователя |
| audit_logs | Неизменяемый через клиент журнал действий |

Дополнения к ТЗ: категория и поля повторяемости дефекта, уникальный `request_id`, читаемый последовательный номер заявки, `acknowledged_at` и `rejected_at`, имя автора в истории. Они обеспечивают повторную безопасную отправку формы, корректный SLA, новую фотографию после отказа и читаемую историю без раскрытия чужих профилей. `private.settings` хранит окно повторных дефектов.

### Что является backend в KEPIL

- `submit_defect`: валидирует поля, блокирует объект на время транзакции, сопоставляет гарантию с текущей датой Актау (включая день окончания), определяет подрядчика, создаёт дефект и заявку, рассчитывает срок реакции/ремонта, записывает историю, аудит и уведомления. Истёкшая или отсутствующая гарантия сохраняет дефект без заявки. Гарантия, которая ещё не началась, не считается действующей.
- Повторяемость: SQL-запрос по тому же объекту и категории за последние 90 дней; возвращает число случаев, ID предыдущих дефектов и интервал. Настройка: `private.settings.repeat_window_days`.
- `transition_claim`: разрешает только OPEN → ACKNOWLEDGED → IN_PROGRESS → REPAIR_SUBMITTED → VERIFIED либо REPAIR_SUBMITTED → REJECTED → IN_PROGRESS. Инспектор не исполняет действия подрядчика; подрядчик не принимает свой ремонт. ADMIN может выполнить любой допустимый переход.
- SLA: CRITICAL — 4 часа / 1 день; HIGH — 12 часов / 3 дня; MEDIUM — 24 часа / 7 дней; LOW — 24 часа / 14 дней. «Срок близко» означает ≤24 часов. Сначала контролируется реакция, затем ремонт. На проверке ремонт не накапливает текущую просрочку; поздняя отправка фиксируется в аудите.
- `record_evidence`: проверяет владение, состояние заявки, наличие файла в Storage, владельца, MIME и размер. После отказа требуется файл, фактически загруженный после `rejected_at`, а не поздно зарегистрированный старый файл.
- Сервер декодирует JPEG/PNG/WebP через sharp, сверяет MIME, ограничивает файл 3 МиБ и 25 мегапикселями, отклоняет повреждённые и многостраничные изображения. Лимит выбран с запасом под multipart-запрос к Vercel. Storage приватен, подписанные ссылки живут 10 минут. Метаданные и загрузка не являются единой транзакцией: при ошибке регистрации сервер пытается удалить несвязанный файл.
- `warranties_overview`: PostgreSQL рассчитывает текущий статус, оставшиеся дни и положение на шкале гарантии. Все экраны получают результат с сервера; клиент не решает, действует ли гарантия. Неконечные даты (`infinity`) запрещены ограничениями БД.
- `save_registry`: ADMIN создаёт/редактирует четыре реестра. Проверяет даты, соответствие подрядчика договору и отсутствие пересекающихся гарантий. Связи с уже существующей историей нельзя незаметно переназначить.
- `refresh_sla`: фиксирует обнаруженную просрочку при чтении рабочей области, без дублирования события для этапа. Фонового cron в MVP нет.
- История, аудит и уведомления фиксируются в транзакциях с бизнес-операциями. Прямое редактирование этих таблиц пользователем запрещено.

### Server Actions / RPC

| Server Action | Операция |
|---|---|
| loginAction / logoutAction | Supabase Auth, cookie-сессия |
| submitDefectAction | Zod → submit_defect |
| transitionAction | transition_claim |
| uploadAction | Проверка файла → приватный Storage → record_evidence |
| saveRegistryAction | ADMIN → save_registry |
| readNotificationsAction | mark_notifications_read |

`src/proxy.ts` обновляет cookie-сессию. `getProfile` проверяет пользователя через `auth.getUser`, не доверяет неподтверждённой cookie. `GET /api/health` сообщает наличие конфигурации; **не выдаёт его за проверку подключения к БД**.

## Экраны

`/` — оперативный dashboard и диаграмма статусов; `/assets` и `/assets/[id]` — фильтры, паспорт, гарантия и история; `/defects/new` — регистрация; `/claims` и `/claims/[id]` — SLA, доказательства и приёмка; `/contractor` — кабинет подрядчика; `/inspector` — очередь приёмки; `/registry` — административное редактирование; `/notifications` — события; `/system` — архитектура для жюри.

## Точный сценарий для жюри

1. После миграции и seed войти как `admin@kepil.demo`, открыть dashboard.
2. Открыть `AKT-W-001`, «Водопроводная сеть · 12 мкр.». Показать гарантию до **12 февраля 2028**, договор и Каспий Су Сервис.
3. «Сообщить о дефекте»: категория «Утечка трубы», критичность «Высокая», заголовок и описание от 10 символов.
4. Сохранить. Показать найденную гарантию, **фактическое вычисленное** число оставшихся дней, подрядчика, номер заявки и повторяемость. Число 503 не зашито в UI.
5. Выйти; войти как `contractor@kepil.demo`. Открыть новую заявку → «Принять заявку» → «Начать ремонт».
6. Загрузить свою фотографию PNG/JPEG/WebP, выбрать «После ремонта», нажать «Сохранить фотографию», затем «Отправить на проверку».
7. Выйти; войти как `inspector@kepil.demo`. В «Приёмке работ» открыть заявку, проверить фото и нажать «Принять ремонт».
8. Показать VERIFIED / «Подтверждена», даты, историю, аудит и обновившиеся показатели dashboard.
9. Создать ещё один дефект WATER_LEAK на AKT-W-001. Показать новый `repeatCount` и историю предыдущих случаев.
10. Дополнительная проверка: AKT-W-010 имеет истёкшую гарантию; дефект сохраняется без автоматической заявки. У AKT-W-014 гарантия не зарегистрирована.

Все названия подрядчиков, контакты, договоры, инфраструктурные записи и исторические события — **вымышленные демонстрационные данные**, не официальные сведения акимата. Начальные подтверждения — явно маркированные иллюстрации, не фотографии реальных работ. Новые операции исполняют реальные правила БД и сохраняются в ней.

## Проверки

```powershell
npm run lint
npm run typecheck
npm test
npm run build
```

После настройки реального демо-проекта: `npm run test:live`. Скрипт входит обычными демо-аккаунтами через Auth, создаёт дефект, проходит стадии, загружает и скачивает файл из настоящего приватного Storage, проверяет изоляцию другого подрядчика, принимает ремонт, проверяет аудит/историю и источник dashboard, создаёт повторный дефект. Он **сохраняет тестовые заявки** с пометкой `LIVE TEST` в демонстрационной базе и не предназначен для производственной базы. В текущей сессии этот скрипт не выполнялся из-за отсутствия `.env.local` и выбранного облачного проекта.

Тесты используют PGlite — настоящий PostgreSQL-движок в изолированном тестовом процессе, а не хранилище приложения. Схемы `auth` и `storage` в тестах содержат минимальные совместимые таблицы; функции, транзакции и RLS KEPIL исполняются реально. Отдельный тест проходит полный сценарий под `SET ROLE authenticated` и проверяет изоляцию заявок, дефектов, истории, аудита и Storage.

Проверены: активная/истёкшая гарантия, выбор подрядчика, повторяемость, идемпотентность, переходы и роли, обязательное фото, отказ с причиной, новая загрузка после отказа, запрет прямого UPDATE, SLA и входные данные. Статус финальных проверок — `docs/delivery-report.md`.

При продолжении добавлены проверки отсутствующей/будущей/нескольких гарантий, включённого дня окончания, неверных и бесконечных дат, отсутствующего подрядчика, исключения других категорий и старых дефектов из повторяемости, повреждённых изображений и лимита загрузки. Всего 24 теста.

Визуальный QA **ещё не выполнен**: в сессии нет доступного браузера и рабочей облачной базы. После подключения проверить все перечисленные экраны на 1440, 1024 и 390 px, клавиатуру, навигацию, таблицы, ошибки входа, отклонение ремонта и фото. Адаптивные стили, состояния загрузки/ошибки, подписи полей и focus-visible уже реализованы.

## Развёртывание Vercel

После выбора и настройки Supabase:

1. Создать Vercel-проект из этой папки с preset Next.js.
2. Добавить **только** `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` в нужные окружения Vercel.
3. Выполнить `vercel deploy --prod`, затем указать домен приложения в Site URL / разрешённых URL Supabase Auth.
4. Проверить `/login`, вход каждой роли, полный сценарий, Storage и RLS в облаке. Для демо с доступом жюри отдельно проверить настройки защиты deployment.

Публикация из текущей сессии отклонена автоматической проверкой: требуется явное разрешение на отправку исходников в Vercel-аккаунт `nerfalmiralti-5552`. Обход отказа не выполнялся. Для нового Supabase требуется выбор организации и подтверждение стоимости через инструмент.

## Границы MVP

- Нет интеграции с государственными реестрами, ЭЦП, GIS, SMS/email, Realtime или AI.
- Регистрация даты дефекта — время сервера; произвольное заднее число не принимается.
- Учётные записи создаёт администратор/seed; самостоятельной регистрации и UI управления пользователями нет.
- Повторяемость основана на точном совпадении категории, не на анализе текста.
- Dashboard загружает видимые записи порциями; для промышленного объёма нужны агрегаты SQL и серверная пагинация.
- Сроки инспекторской приёмки отдельно не нормируются. Просрочки фиксируются при обращениях, без фонового планировщика.
- Нет карантина/антивируса загружаемых изображений, гарантированной очереди очистки сирот Storage и юридически значимого хранения документов.
- Для продакшена нужны резервное копирование, мониторинг, политика доступа муниципалитета и проверка реальных данных.

Исходная папка была пустой; сохранять существующую реализацию не требовалось.
